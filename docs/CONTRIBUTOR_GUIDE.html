This guide starts with why the project is worth your time, then covers setup, the branch rules and the workflow for getting your changes merged.

Why Process2Diagram

Meetings are where knowledge is created.
Most of it is lost when the call ends.

Teams spend hours in meetings where processes get explained, rules get agreed and requirements get negotiated. Afterwards, someone takes partial notes and the rest disappears. Process2Diagram takes the raw transcript and, through a pipeline of specialised AI agents, produces what a business analyst would spend days writing: process models, requirements, business rules and minutes, all traceable back to who said what.

What makes it interesting to work on

🧠

Real multi-agent orchestration

Agents share one central state (KnowledgeHub) and never call each other directly. Some run in parallel, and BPMN has a LangGraph adaptive-retry loop plus a "tournament" of runs scored by a deterministic validator.

📐

Grounded in OMG standards

The output isn't free-form text. It's BPMN 2.0 (ISO/IEC 19510), SBVR business vocabularies and rules, BMM business models and DMN decision tables, the languages enterprise architects already use.

🛠️

LLM + deterministic code

LLMs extract meaning, and pure Python enforces correctness: a 4-pass BPMN auto-repair, structural validators, rule enforcement and Pydantic output schemas. The two sides are built to cover each other's weaknesses.

🔎

A RAG assistant with tools

Ask questions across every meeting of a project. The assistant runs tool calls against Supabase + pgvector to query requirements, compare meetings, draw charts or generate executive decks.

🔐

Privacy by design (LGPD)

A two-tier PII sanitiser replaces CPFs, emails, amounts and people's names before anything reaches an LLM, then restores them afterwards. API keys never touch disk.

📊

Measures meeting quality

Beyond extraction, it scores meetings: a type-aware ROI dashboard, a knowledge graph of entities and contradictions, argument mapping (IBIS) and evidence-grounded "provocations" about what was left unsaid.

🏛️

Institutional memory that learns (CKF)

Every project has a Context Knowledge File: a living Markdown document with key people, glossary, known processes, permanent rules and strategic goals. All agents read it before analysing a transcript, and the AgentCKFUpdater enriches it after each meeting. The more meetings it processes, the better it knows the client's business.

💸

Cost control built in

Each agent can use a different model. The Cost-Benefit Scenarios page compares up to five agent→model combinations before you process anything, a PII-safe SHA-256 cache avoids paying twice for identical calls, and long transcripts (>50k tokens) are detected automatically.

Behind the project

Pedro Gentil Regato de Oliveira Soares is a statistician and senior BPM specialist, and an IBM Redbook author. His path runs from process automation to AI in production. Process2Diagram is his personal research project, built from the conviction that the knowledge created in corporate meetings is the most wasted strategic asset in modern organisations, and that generative AI, guided by formal standards, turns conversation into governance.

What you'll get out of contributing

  • Hands-on applied AI engineering: multi-agent design, prompt and skill versioning, LLM telemetry, semantic caching and fail-open architecture in a codebase that actually ships.
  • A live product: every merged PR deploys to Streamlit Cloud, so your work is in users' hands the same day.
  • Room to own something: there are open fronts in BPMN layout, new agents, evaluation, UX and the commercial API. Pick one and make it yours.
  • A collaborator who documents decisions: architecture, pitfalls and the reasoning behind each change are written down, so you won't have to guess.

1The project in one page

Process2Diagram is a Streamlit platform that takes a meeting transcript (pasted text, .txt, .docx or .pdf) and uses a multi-agent, multi-LLM pipeline to produce business artifacts: BPMN 2.0 diagrams, Mermaid flowcharts, meeting minutes, IEEE 830 requirements, an SBVR vocabulary, a BMM model and an executive HTML report. Everything is stored in Supabase (PostgreSQL + pgvector), and a RAG assistant answers questions about it.

Secrets and API keys

  • Copy .streamlit/secrets.toml.example to .streamlit/secrets.toml and ask Pedro which values to use (Supabase URL/key, login credentials).
  • LLM API keys (DeepSeek, OpenAI, Anthropic, Gemini, Groq, Grok…) are entered in the app UI. They live only in st.session_state and are never written to disk.
  • The app is fail-open: without Supabase configured, most pages still load and return empty data instead of crashing.
Never commit secrets.toml, .env, Google credential JSONs or any API key. They're in .gitignore; don't force-add them.

4How main is protected

Every push to main auto-deploys to Streamlit Cloud, so main is production. A GitHub ruleset ("Protect main") enforces the following:

🔀 Pull request required

Changes reach main only through a PR. Direct pushes are rejected.

✅ 1 approving review

Pedro reviews and approves each PR. If you push new commits, the existing approval is dismissed.

💬 Conversations resolved

All review comments must be resolved before merging.

🛡️ No force-push / no deletion

The history of main can't be rewritten and the branch can't be deleted.

Pedro, as repository admin, can bypass these rules to keep his own direct-to-main workflow. For everyone else, PRs are the only route.

Pedro pushes to main often, so rebase your branch before asking for review:

git fetch origin
git rebase origin/main
git push --force-with-lease         # OK on YOUR branch — never on main

What makes a good PR

  • One topic per PR. Small PRs get reviewed and merged faster.
  • Describe what changed, why, and how you tested it. Add screenshots for UI changes.
  • Mention any Supabase migration (setup/*.sql) explicitly. Pedro runs migrations manually.
  • Mark the PR as Draft if you want early feedback.

6Code conventions (non-negotiable defaults)

AreaRule
New agentsInherit from BaseAgent, set name and skill_path, and implement build_prompt() and run(). Register the agent in Orchestrator._PLAN and core/rerun_handlers.py.
OrchestrationNever instantiate agents directly from app.py or pages. Always go through Orchestrator or handle_rerun().
KnowledgeHubAdd each new field together with a guard in KnowledgeHub.migrate(). No scattered hasattr checks.
Skill filesUse lowercase filenames (skills/skill_xxx.md). Streamlit Cloud runs on Linux and is case-sensitive, so check with git ls-files skills/.
SupabaseAlways fail-open: return [] or None and never let an exception reach the UI.
Active projectUse require_active_project(). Never add a local project selectbox to analysis pages.
Assistant toolsImplement the method in the matching mixin in core/tools/, add its schema to that file's *_SCHEMAS, and register it in AssistantToolExecutor.execute(). Don't add methods to core/assistant_tools.py.
DependenciesPin exact versions (pkg==1.2.3) in requirements.txt. No version ranges.
Security / LGPDKeep API keys in st.session_state only. Don't bypass the PII sanitizer in BaseAgent._call_llm().
DraftsPut conceptual blueprints in drafts/. Once a draft is implemented, move it to drafts/arquivadas/; don't delete it.

7Known pitfalls worth knowing on day one

  • Don't use the GitHub web editor on large files. It once replaced a 3,500-line file with a 93-line stub. Use your IDE and the CLI.
  • st.download_button triggers a full rerun. Store hub in st.session_state before rendering widgets.
  • Nested st.expander raises an exception. Use a caption or markdown header instead.
  • href="#id" inside components.html navigates the parent frame. Use data-target + scrollIntoView.
  • Anthropic has no JSON mode. Enforce JSON through the system prompt and never pass response_format.
  • Mermaid: avoid the node IDs END, START and default, and use {} (not {{}}) for decisions.

The full list with code examples is in claude_guideline/pitfalls.md.

8Working with Claude Code

The project is built largely with Claude Code. If you use it too:

  • CLAUDE.md at the repo root is loaded automatically and holds the architecture map, rules and checklist. Keep it accurate when you change structure.
  • Larger changes are specified as PCs (Project Change documents): structured Markdown specs with file-level detail. Reference the PC number in your branch or PR when there is one (e.g. feat/pc210-…).
  • Always review AI-generated diffs yourself before opening a PR. The approval rule still applies.

9PR checklist

  • Branch created from an up-to-date main and rebased before review
  • pytest tests/ passes locally
  • App starts with streamlit run app.py and the changed pages work
  • KnowledgeHub.migrate() updated if the hub changed
  • Skill filenames verified with git ls-files skills/
  • New agent registered in Orchestrator._PLAN and rerun_handlers; tab registered in ui/tabs/__init__.py
  • New dependencies pinned with exact versions
  • No secrets, credentials or personal data in the diff
  • Supabase migrations (if any) called out in the PR description
  • Version or change noted in claude_guideline/roadmap.md when it's a feature

10Good first issues (found on a live tour)

While preparing this guide we processed the Aurora demo in the deployed app and found the issues below. Each one is real, reproducible and confirmed in the code. They're scoped so you can learn the codebase while shipping something useful. Pick one and open a Draft PR.

UI bug

Currency values in the assistant render as LaTeX

~1 h

Answers that mention amounts like R$ 500 mil até R$ 2 milhões come out garbled. Streamlit's st.markdown reads text between two $ signs as KaTeX math. In a Brazilian banking context, almost every answer mentions R$.

Where: pages/Assistente.py lines ~619 and ~1688, st.markdown(msg["content"]). Fix idea: escape $ (.replace("$", r"\$")) in one shared render helper, and check the HTML/Markdown exports too. Add a regression test.

Correctness

The assistant gets wrong who proposed a decision

~1–2 days

Asked who proposed the score-band rule and the approval limits, the assistant credited Beatriz (BM) for everything. The transcript says otherwise: the score bands were proposed by Marcos (MC, 10:17) and the approval limits by Paulo (PHS, 10:19). Beatriz only formalised them as Requirement 14 afterwards. For a product that sells traceability, attribution has to be exact.

Where to start: how map_transcript_to_requirements and search_transcript return speaker lines (core/tools/). The answer itself admits it inferred the author "from the continuity of the enumeration". Fix idea: return the speaker tag with every transcript chunk, and tell the assistant to cite only speakers it has actually seen. Use Aurora R1 as the golden test.

Cost

One question cost ~495k tokens and 16 tool calls

~2–3 days

That single question triggered get_requirements 3×, get_sbvr_rules 2× and search_transcript 2×, among others, for 494,626 tokens. The full pipeline for the whole meeting used 276k. Repeated identical tool calls within one turn are pure waste.

Fix idea: memoise tool results per turn in AssistantToolExecutor.execute() (same name and args → cached result), trim large tool outputs before feeding them back, and show a per-turn token budget. The LLMTelemetry data will show the before and after.

UI bug

The Mind Map opens as a tiny speck until you click "fit"

~2 h

On Diagramas → Mind Map the map draws in the top-left corner at near-zero size. It's the same family of bug as the documented bpmn-js fit-viewport pitfall: the component lays itself out while its tab is hidden, so it measures a 0×0 container.

Where: modules/mindmap_interactive.py. Fix idea: defer the initial fit until the container has a non-zero size (a ResizeObserver or a guarded setTimeout), as modules/bpmn_viewer.py already does.

Polish

Running BPMN passes show a red ❌

~15 min

While the BPMN tournament runs, the progress log shows ❌ BPMN Agent — pass 1/3…, which looks like a failure. The pipeline emits the status "pass 1/3…", and the icon mapper only knows done / running / skipped, so anything else falls through to ❌.

Where: pages/Pipeline.py → update_progress() (~line 278) and core/pipeline.py line 54. Fix idea: map "pass" to ⏳, or emit "running — pass 1/3". Your first PR could be this one.
